# Разделение обычного и БС-трафика

> Дополнительный режим для тарифов и мультиподписок. Перед включением проверьте настройки панели и ограничения учёта ниже. Обновляйте бот и кабинет вместе, предварительно сохранив резервную копию базы.

## Что меняется

Разделение включается в настройках конкретного тарифа. Классический режим его не использует. У подписки остаются прежняя учётная запись Remnawave и ссылка подключения. Установка дополнительных программ рядом с нодами не требуется.

Оператор выбирает внутренние сквады обычной группы и БС-группы. Каждая группа получает собственный лимит и пакеты докупки; нулевой лимит означает безлимит. БС-докупка доступна только для конечного лимита с настроенными пакетами. Расход БС не списывается с обычного остатка и наоборот. Исчерпание одной группы снимает доступ только к ней, сохраняя другую оплаченную группу.

Для операторов, которые разделение не включали, сохраняется прежний сценарий покупки и учёта.

## Подготовка панели

Обычная и БС-группа должны использовать разные ноды. Разные инбаунды на одной ноде не дают раздельного счётчика расхода пользователя в доступном контракте API. Поэтому такое пересечение для двух платных групп отклоняется при проверке. Grace может использовать ту же ноду с отдельным инбаундом: его доступ и период обрабатываются отдельно от платных остатков.

Панель должна сохранять пользовательскую статистику: `disableUserUsageRecords=false`, `cleanUsageHistory=false`, `userUsageIgnoreBelowBytes=0`. При сохранении включённой настройки бот проверяет конфигурацию панели и фактический состав сквадов. Неудачная проверка не сохраняет новую конфигурацию тарифа.

Первое включение связывает учёт с текущей панелью. Смена ключа доступа не создаёт новую панель. Смена её адреса, восстановление другой базы или замена панели требуют отдельной сверки существующих подписок; автоматического переноса по совпадающему числовому ID пользователя нет.

Внешний сквад не заменяет внутренние сквады и не является источником раздельных счётчиков. Его существующие правила применяются отдельно.

## Границы точности

Панель отдаёт накопительные показания, а не время передачи каждого байта. Обновление показаний может запаздывать. Два одинаковых ответа API не доказывают, что весь предыдущий расход уже поступил.

В проверенной версии Remnawave 3.4.8 запись пользовательской статистики в историю выполняется через [очередь с задержкой 120 секунд](https://github.com/remnawave/backend/blob/3.4.8/src/queue/push-from-redis/push-from-redis.service.ts). На локальном стенде новые показания появлялись примерно через 125–135 секунд; это наблюдение, а не гарантированный максимум. Более частый опрос ботом не ускоряет запись внутри панели. Поэтому остатки и снятие доступа опираются на уже поступившую статистику; задержка может увеличиваться при нагрузке или недоступности панели.

Спорный расход не списывается с нового оплаченного пакета. Настройка `BS_TRAFFIC_UNCERTAIN_WRITE_OFF_ENABLED` разрешает принять возможный недоучёт такого пограничного расхода. Это явный выбор оператора, а не дополнительная плата клиенту и не разрешение переносить старый перерасход на новую покупку. Перед включением необходимо прочитать пояснение настройки.

Задержка статистики, очереди запросов и существующие соединения могут дать перерасход после исчерпания лимита. Чем выше скорость передачи до получения показаний и применения ограничения, тем больше возможный перерасход. Бот не обещает побайтовый учёт или жёсткое ограничение величины перерасхода, в том числе при доступной панели.

## Завершение существующих соединений

`BS_TRAFFIC_FORCE_DISCONNECT_ENABLED` по умолчанию выключена. После подтверждённого снятия доступа настройка разрешает запрос завершения соединений пользователя на нодах исчерпанной группы.

Механизм панели работает по IP. Он может прервать соединения других клиентов за тем же общим адресом, например у мобильного оператора или в одной сети Wi-Fi. Это ограничение штатного механизма панели; бот не устанавливает собственный агент на ноды.

Перед запросом снова проверяются принадлежность подписки, оплаченный срок, остатки, отсутствие grace, текущий состав нод и включённая настройка. Ответ `202` означает принятие запроса, а не доказанное завершение всех соединений. После неизвестного результата запрос автоматически не повторяется. Ноды другой платной группы не добавляются к запросу.

Штатному механизму нужны эффективная capability `NET_ADMIN` у процесса ноды и поддержка `CONFIG_INET_DIAG_DESTROY=y` в работающем ядре Linux-хоста. Контейнер использует ядро хоста; для Docker Desktop это ядро его Linux-VM, где поддержка может отсутствовать даже при современной версии ядра. Установка пакета внутри контейнера или включение настройки бота не добавляет отсутствующую возможность ядра. Требования панели к нодам и смысл whitelist описаны в [официальной инструкции Remnawave](https://f.docs.rw/t/topic/205); параметр `connectionDrop.enabled` управляет настройкой whitelist, а не включает само удаление соединений.

Если ядро предоставляет `/proc/config.gz`, его конфигурацию можно прочитать внутри контейнера штатным Node.js, без установки дополнительных программ (замените `remnawave-node-example` на имя своей ноды):

```sh
docker exec remnawave-node-example node -e 'const fs=require("fs"),z=require("zlib"); console.log(z.gunzipSync(fs.readFileSync("/proc/config.gz")).toString().split("\n").filter(s=>s.includes("CONFIG_INET_DIAG_DESTROY")).join("\n"))'
```

Строка `# CONFIG_INET_DIAG_DESTROY is not set` подтверждает отсутствие поддержки. Если файл отсутствует, результат неизвестен: нужна конфигурация именно работающего ядра, доступная оператору хоста. В Linux [TCP-обработчик удаления](https://github.com/torvalds/linux/blob/master/net/ipv4/tcp_diag.c) зависит от этой опции; [диагностический интерфейс](https://github.com/torvalds/linux/blob/master/net/ipv4/inet_diag.c) возвращает `EOPNOTSUPP`, когда обработчика нет.

В проверенном контракте панели 3.4.8 / ноды 3.4.3 API сообщает версии и состояние подключения ноды, но не конфигурацию ядра и не результат удаления отдельных сокетов. Даже завершённое задание панели с `success=true` не подтверждает закрытие: состояние `connection_drop=accepted` означает только принятую команду. Отдельное состояние доставки `verified` подтверждает состав сквадов после изменения доступа. Перед использованием разрыва оператору нужна проверка уже открытого соединения на своём стенде; успешная блокировка нового подключения её не заменяет.

## Покупка и отображение

Покупка сохраняет сумму, выбранную группу, срок пакета и идентификатор операции в одной транзакции. Повторная проверка той же покупки не должна списывать деньги повторно. Если панель временно недоступна, интерфейс показывает ожидание применения; это не новая покупка.

Уже оплаченная докупка исполняется по сохранённым условиям. Последующая правка предложения тарифа не переносит её на другой сквад и не отменяет оплаченный остаток. Фактическое изменение или удаление сквадов в панели требует сверки: локальная конфигурация не доказывает, что прежний доступ ещё существует.

Календарное обновление базы не списывает деньги и не продлевает подписку. Используются сохранённые оплаченные условия. Докупки учитываются отдельно от базового лимита.

При смене одного суточного split-тарифа на другой оплаченные сутки и время следующего суточного списания сохраняются. Доплата — положительная разница полных суточных ставок, пропорциональная оставшемуся времени; дробная копейка отбрасывается. При переходе на более дешёвый тариф возврата нет. Следующие сутки оплачиваются по полной новой ставке. Бот и кабинет используют один серверный расчёт и показывают сумму до подтверждения.

Для такого перехода необходим сохранённый подтверждённый платёж за текущие сутки. Если его условия нельзя доказать по истории, например после ручного изменения срока, смена не списывает деньги. Следующая штатная суточная оплата сохраняет новый подтверждённый интервал. Переход между суточным и периодическим режимами этим механизмом не поддерживается.

Для периодических тарифов реализована смена календаря обновления лимита, в том числе вместе с переходом между конечным лимитом и безлимитом и проверенной сменой состава нод. Исходные условия берутся из оплаченной операции: последующее редактирование тарифа оператором не меняет их задним числом. Оплаченный срок и отдельные пакеты докупки сохраняются. Для включения конечного лимита сначала подтверждаются исходные показания; поздний спорный расход не списывается из новой базы.

Проверенная смена тарифа поддерживает добавление, удаление и возврат нод, перенос ноды между группами, а также одновременную смену состава нод с режимом лимита или календарём. Прежний внутренний сквад нельзя назначить противоположной группе; обычная и БС-группа по-прежнему не должны пересекаться по нодам. До списания проверяются прежний и целевой составы, а для ноды, входящей в группу с конечным лимитом, — свежие исходные показания. Изменение состава прежнего сквада непосредственно в панели не заменяет проверенную смену тарифа. Переход использует существующий аккаунт; счётчики панели не сбрасываются.

История сохраняет отдельные периоды владения нодой с группой и условиями перехода. Для входа в группу с конечным лимитом дополнительно фиксируются исходные показания. Первый положительный прирост после такого входа сохраняется как спорный расход или списывается в недоучёт только при включённой настройке оператора; последующие измеренные приросты обрабатываются по текущим правам. Это ограниченная проверка границы перехода, а не доказательство поступления всей старой статистики. Один накопительный счётчик за день не обрабатывается независимо двумя историческими записями.

Поздние показания удалённых нод сохраняются отдельно от новых остатков. Сбор ограничен по числу заданий и исторических дней, чтобы не вытеснять текущий учёт других подписок. Исчерпание этих ограничений означает необходимость сверки, а не нулевой расход или завершённый учёт. Само наличие исторических записей больше не запрещает повторное включение через новую покупку. Для него нужны подтверждённый возврат к обычному учёту, сохранённые оплаченные условия и свежие исходные показания перед новым переходом. Старые записи и спорный расход сохраняются со своим прежним периодом владения; они не получают права списывать новую оплаченную базу. Если условия нового перехода не подтверждены, оплаченная операция остаётся ожидающей применения. Обычное продление действующего разделения не создаёт нового периода сбора старой ноды.

Пока оплаченная смена сквадов не применена, новая оплата продления активной подписки недоступна. Бот и кабинет показывают пояснение до создания корзины. Если срок уже закончился, новое продление сохраняет незавершённый переход и выдаёт только вновь оплаченные права; подтверждённый grace обрабатывается отдельно. Неизвестный результат ранее отправленной записи сначала проверяется чтением панели — повторная отправка вслепую не выполняется.

## Выключение и grace

Выключение разделения прекращает новые продажи БС. Уже оплаченные права сохраняются до зафиксированного срока; обычное продление не продлевает этот срок БС. После завершения обязательств предусмотрен обратный переход к обычному учёту без обнуления счётчиков и без второй учётной записи. Незавершённые операции и спорные данные должны быть обработаны до перехода.

Исчерпание только БС при доступном обычном трафике не является основанием выдавать grace. Grace рассматривается при окончании срока или подтверждённом исчерпании обоих платных доступов по его собственным настройкам. Временный grace-доступ не превращается в оплаченный остаток.

## Обновление и диагностика

Перед обновлением сохранить резервную копию PostgreSQL. Бот и кабинет обновляются согласованно. Миграции сохраняют историю платежей, выдачи и неизвестных результатов внешних запросов; удалять эти записи вручную для повторной отправки нельзя.

Проверять нужно завершённый сбор и обработку показаний, возраст очередей и неподтверждённые операции. Сам факт работы фоновой задачи не означает исправный учёт. При проблеме сохранить версию бота и панели, время события и идентификатор внутренней операции; не публиковать токены или ссылки подключения.

В кабинете состояние доступно в разделе **Remnawave → Обзор → Раздельный трафик**. Показываются время снимка и последнего успешного полного цикла, допустимый возраст цикла, этап сбора, незавершённые задачи и причины, требующие проверки. Можно вручную обновить снимок. Сбой чтения скрывает прежнее успешное состояние и предлагает повторить обновление; отсутствие свежих данных не считается исправным учётом.

Диагностика читает сохранённое состояние PostgreSQL и не выполняет восстановление или запросы к панели. Доступ требует права `remnawave:read`; API `GET /cabinet/admin/remnawave/split-diagnostics` возвращает только агрегаты без клиентских идентификаторов и сырых ошибок. За один запрос показываются не более 16 активных подключений с явным предупреждением, если часть не проверена. Состояние фонового сервиса в другом процессе может быть неизвестно; общая проверка учёта не заменяет проверку покупки конкретной подписки и не подтверждает закрытие соединений.

Для показаний удалённых нод предупреждение `Split removed node tail requires attention` в логах сохраняет причину и идентификатор исторической записи. Счётчик исторических записей в кабинете может включать несколько периодов одной ноды; счётчики сбора относятся к отдельным задачам по дням. Нормально завершённый прежний период при повторном включении архивируется без предупреждения; действительно спорные записи остаются видимыми. Не удаляйте историю для обхода проверки повторного включения.
