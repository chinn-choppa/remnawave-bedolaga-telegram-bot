# Управление регистрацией по приглашениям из Cabinet

## Источник настроек

В системных настройках Cabinet откройте категорию **«Регистрация и доступ»**.
Два параметра доступны через существующий API:

- `INVITE_ONLY_ENABLED`: ограничивает **создание новых аккаунтов** приглашениями.
- `INVITE_ONLY_ALLOW_GIFT_LINKS`: допускает подходящие подарочные ссылки как приглашения.

Значения по умолчанию в коде: `false` и `true` соответственно. Когда эти ключи явно установлены в окружении (`.env`, переменные контейнера, настройки запуска), приоритет остаётся у окружения. Cabinet должен показывать такие значения как `env_locked` и **не** разрешать их править.

## Перенос управления с .env на Cabinet

Не изменяйте рабочую конфигурацию без штатного разрешения и возможности отката.

1. **До изменения** проверьте эффективные значения обоих параметров в административном интерфейсе, наличие у администратора прав `settings:read` и `settings:edit` и работоспособность входа в Cabinet. Зафиксируйте исходные значения без публикации самого `.env`.
2. Учитывайте, что API запрещает изменение ключей, закреплённых окружением: предварительно выставить их значения через Cabinet нельзя. Если текущее значение отличается от программного значения по умолчанию (например, `INVITE_ONLY_ENABLED=true`), **просто удалять переменную из окружения нельзя**: при первом запуске ограничение регистрации может временно отключиться.
3. Подготовьте отдельный разрешённый план перехода: на время обслуживания закройте **публичные** входы регистрации и оставьте доступ администратора, либо предварительно сохраните эквивалентные значения в `system_settings` через специально согласованный безопасный механизм миграции. Штатный Cabinet API не поддерживает предварительную запись заблокированного ключа; не обходите ограничение прямыми SQL-командами.
4. Уберите **только** `INVITE_ONLY_ENABLED` и `INVITE_ONLY_ALLOW_GIFT_LINKS` из источника окружения (включая Docker/Compose overrides), затем выполните штатный перезапуск процессов. Пока публичный вход закрыт, установите и проверьте исходные значения через Cabinet.
5. Убедитесь, что настройки больше не обозначены как `env_locked`, а переключение из Cabinet меняет эффективное состояние. Только после этого открывайте публичную регистрацию в требуемом режиме.
6. Проверьте отдельные сценарии: новый пользователь без приглашения; новый пользователь с корректным приглашением; существующий пользователь; подтверждённый администратор; разрешённая/запрещённая подарочная ссылка. **Не** используйте реальные клиентские данные для пробных регистраций.

Если изменение в шаге 3 невозможно выполнить атомарно, не пытайтесь компенсировать это отключением ограничений доступа. Используйте заранее согласованное окно и проверку доступа после перезапуска.

## Откат

Верните первоначальные значения двух переменных окружения, перезапустите затронутые процессы штатным способом и повторите проверки входа и регистрации. Настройки `system_settings` при этом будут перекрыты значениями из окружения.

## Согласованность процессов

Обработчик входа Cabinet должен вызывать `RegistrationAccessService` вместо ранней проверки снимка `settings.INVITE_ONLY_ENABLED`. Сервис читает значение из `system_settings`, если нет приоритета окружения, и возвращает `CHECK_UNAVAILABLE` при ошибке чтения. Для новой регистрации это означает отказ (HTTP 503), а не неявное разрешение. Действующие пользователи и подтверждённые администраторы проверяются центральной политикой отдельно.

Публикация или слияние этой инструкции **не** означает, что новая политика применена в рабочей среде.
